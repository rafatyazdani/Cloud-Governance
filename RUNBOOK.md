# Security Incident Runbook

This runbook covers the response procedures for alerts generated by this toolkit. When the SNS topic fires, use this document to triage and respond.

---

## Alert Triage Flow

```
SNS alert received
       │
       ▼
1. Open Security Hub → Findings
2. Filter by severity: CRITICAL / HIGH
3. Identify finding type (see sections below)
4. Follow the relevant response procedure
5. Document actions taken in your incident log
```

---

## Finding Type: Credential / IAM Anomaly

**GuardDuty finding types:** `UnauthorizedAccess:IAMUser/*`, `Recon:IAMUser/*`, `Impact:IAMUser/*`

**What it means:** An IAM credential is being used in an unusual way — new region, unusual API calls, high-volume enumeration, or known malicious IP.

**Immediate actions (first 15 minutes):**
1. Identify the affected IAM principal from the finding detail
2. Check CloudTrail for the last 2 hours of activity by that principal:
   ```
   aws cloudtrail lookup-events \
     --lookup-attributes AttributeKey=Username,AttributeValue=<principal> \
     --start-time $(date -d '2 hours ago' --iso-8601=seconds)
   ```
3. If activity looks malicious — **disable the credential immediately:**
   ```
   aws iam update-access-key --access-key-id <key-id> --status Inactive
   # or for console users:
   aws iam delete-login-profile --user-name <username>
   ```
4. Capture a snapshot of active sessions before revoking:
   ```
   aws iam list-attached-user-policies --user-name <username>
   aws iam list-user-policies --user-name <username>
   ```

**Investigation (next 1–4 hours):**
- Review all resources created, modified, or deleted by the principal
- Check for new IAM users, roles, or access keys created (persistence mechanism)
- Check for S3 GetObject calls on sensitive buckets
- Check for unusual EC2/Lambda activity

**Escalation trigger:** Any evidence of data access, new IAM entities created, or cross-account activity.

## Finding Type: S3 Public Exposure

**Security Hub finding types:** `S3.2`, `S3.3`, `S3.8` | GuardDuty: `Policy:S3/*`

**What it means:** An S3 bucket has public access enabled, a permissive bucket policy, or is being accessed by unusual principals.

**Immediate actions:**
1. Identify the bucket name from the finding
2. Check current public access settings:
   ```
   aws s3api get-public-access-block --bucket <bucket-name>
   aws s3api get-bucket-policy --bucket <bucket-name>
   ```
3. If publicly accessible — **block public access immediately:**
   ```
   aws s3api put-public-access-block \
     --bucket <bucket-name> \
     --public-access-block-configuration \
       "BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true"
   ```
4. Check CloudTrail for GetObject calls in the past 24–72 hours to assess data exposure scope

**Investigation:**
- Determine what data was in the bucket and its classification
- Check bucket access logs for IPs and volumes accessed
- If PII or sensitive data was exposed — initiate your data breach notification process

## Finding Type: GuardDuty — EC2 Compromise

**GuardDuty finding types:** `Trojan:EC2/*`, `CryptoCurrency:EC2/*`, `Backdoor:EC2/*`, `UnauthorizedAccess:EC2/*`

**What it means:** An EC2 instance is exhibiting malicious behavior — C2 communication, cryptomining, or is being used as an attack tool.

**Immediate actions:**
1. Isolate the instance — modify its security group to deny all inbound/outbound:
   ```
   aws ec2 modify-instance-attribute \
     --instance-id <instance-id> \
     --groups <isolation-sg-id>
   ```
   > Create an "isolation" security group in advance with no rules — attach it here
2. Take a forensic snapshot before any remediation:
   ```
   aws ec2 create-snapshot --volume-id <root-volume-id> \
     --description "Forensic snapshot - incident $(date +%Y%m%d)"
   ```
3. Do **not** terminate the instance until forensic capture is complete

**Investigation:**
- Review VPC flow logs for the instance's private IP — look for C2 beaconing, data exfiltration volume
- Review CloudTrail for API calls made by the instance's IAM role
- Check instance metadata access logs if IMDSv2 is enforced

## Finding Type: CloudTrail or Logging Disabled

**Security Hub finding types:** `CloudTrail.1`, `CloudTrail.2` | Config change on GuardDuty or Security Hub resource

**What it means:** Someone attempted to disable an audit or detection control. This is a high-priority finding — it may indicate an attacker covering their tracks.

**Immediate actions:**
1. Identify the IAM principal that made the change from CloudTrail
2. Treat as a credential compromise (follow IAM Anomaly procedure above)
3. Re-enable the disabled service immediately:
   ```
   aws cloudtrail start-logging --name <trail-name>
   aws guardduty update-detector --detector-id <id> --enable
   ```
4. Verify SCPs are still attached to the org root — an SCP bypass indicates org-level compromise

**This finding always warrants escalation to leadership.**

## Severity Reference

| Severity | Response SLA | Example Finding |
|----------|-------------|-----------------|
| CRITICAL | 15 minutes | Active credential abuse, ransomware indicator |
| HIGH | 1 hour | S3 public exposure, logging disabled |
| MEDIUM | 24 hours | MFA not enabled, unused credentials |
| LOW | 1 week | Minor config drift, informational findings |

---

## Post-Incident

After any CRITICAL or HIGH incident:
1. Document timeline, actions taken, and root cause
2. Run `terraform plan` to verify infrastructure state matches expected — look for drift
3. Review and update this runbook if a gap was identified
4. Consider whether an additional control would have prevented or detected faster
